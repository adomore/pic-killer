## 1. 审计范围与方法

审计对象为 `main` 分支的 `e30adbf` 提交，工作区干净：11 个 Rust 源文件、两套 PowerShell 测试脚本、两个 GitHub Actions 工作流，以及 `README.md`。

按以下顺序使用了三种方法：

- **静态阅读。** 通读全部源文件；41 个分析 agent 提取了逐命令规格，并从四个维度审计——正确性与数据安全、安全性与健壮性、性能、命令行 UX。所有 medium 及以上的候选发现，都交给一个独立的对抗性审阅者去反驳。三条被反驳并剔除。
- **构建与门禁执行。** 在 Windows 11、Rust 1.91.1 上完整构建并跑通全部发版门禁。
- **实弹探测。** 凡是预测了用户可见行为的发现，都拿 release 二进制对真实图片复现。下文标注*已复现*的即由此确认，其余仅基于源码阅读。

发版门禁被完整执行，且**全部通过**：

| 门禁 | 结果 |
|------|------|
| `cargo test --locked` | 51 通过，0 失败 |
| `cargo fmt --all --check` | 干净 |
| `cargo clippy --all-targets --all-features` | 干净，无警告 |
| `cargo build --release` | 成功 |
| `tests/functest.ps1` | 59/59 条断言通过 |
| `tests/perftest.ps1` | 4/4 条断言通过 |

下文的一切，都是在这六道门禁全绿的代码库里发现的。这正是本报告的核心：**门禁没有覆盖到真正会坏的地方。**

**修复。** 这些发现随后被修掉了。每条修复都用当初复现缺陷的同一套操作对重新构建的二进制再跑一遍，确认问题不再出现；每条也都配了以其编号命名的回归断言。端到端断言数从 59 增至 103，并已接入 CI 的 `windows-latest` job；单元测试从 51 增至 73，新增部分集中在原先只有五个测试的 `commands.rs`。各条发现下方带**状态**行；发现本身的描述保持原样不改，好让本文档仍是「当时发现了什么」的记录，而不是「代码现在长什么样」的说明。

## 2. 审计结论

工程基本功很扎实。架构分层干净、无环，所有写入收敛到一个原子替换出口，没有 `unsafe`、没有 `TODO`，手写的 8BIM、APP13、APP1 与 PNG chunk 字节级解析器边界检查完备——对抗性安全审查确认它们不存在内存安全暴露面，`quick-xml` 也没有实体展开攻击面。

缺陷集中在另一处：**工具承诺的事与它实际做的事之间的落差。** 其中三条的分量超过其余全部之和。

- **`strip` 并没有清除。** 这个被描述为「清除全部元数据（保护隐私）」的命令只删 EXIF。XMP 包与 IPTC 块原封不动，连同它们里面的姓名、城市、位置一起留在文件里。命令还报成功。这是一个隐私工具在隐私功能上失效（§6，F-01）。
- **`--where` 可能静默选中全部文件。** 对不存在的标签名做负向比较会匹配一切，`&&` 与 `||` 混用则会静默误解析。两者都把窄筛选变成宽筛选，且发生在会删除元数据的命令上（§6，F-02、F-03）。
- **文档宣传的 CSV 闭环根本跑不通。** `show --csv` 输出五列，`apply` 读三列。把前者喂给后者，每一行都失败（§6，F-04）。

这三条都不是刁钻边角。它们全都长在工具主推的路径上，而六道门禁照样全绿——因为端到端测试里 `strip` 测的是一个只有 EXIF 的文件，而那个闭环从来没被测过。

审计时的评级：**B−。** 代码比产品好。

**修复之后：A−。** 全部致命与高危发现，加上三处 panic 与那条恒真断言，都已修复并配了回归断言。`strip` 现在一次原子写入清掉三套元数据；`--where` 对「混用运算符」和「未知标签名」两个陷阱都改为报错而不是静默放大范围；`show --csv --for-apply` 让文档写的闭环真正成立；sidecar 冲突被拒绝且写入已原子化；`verify` 能区分「没有元数据」与「元数据损坏」。其余中等发现此后也已全部关闭，只剩 F-17 中「多条件共享一次读取」那一半。仍然压着评级的是：`commands.rs` 依旧占生产代码的 41%，虽然单元测试从 5 个增加到 22 个，但覆盖的是它的纯函数而非命令体本身 —— 后者仍然只有端到端层在测。

## 4. 架构评审

模块图是干净的五层结构，依赖严格向下、无环：入口 → 声明式 CLI → 编排层 → 三个元数据引擎 → 纯逻辑工具。

有两个结构决策值得记功，因为正是它们让一个 5,700 行的工具保持了内聚：

- **唯一的写出口。** 整个程序的每一次写入都经过 `exif::commit_raw`，备份、原子替换、时间戳保护三件事都归它管。新加的命令自动继承这三重保证，且无法意外绕开。唯一绕开它的地方是 sidecar 写入——而那里恰好就出现了一个数据损坏缺陷（F-05）。
- **唯一的批处理骨架。** `run_batch` 独占并行度、进度条、三态统计与汇总输出。十个写入命令共用同一份实现。

弱点在于体量分布。`commands.rs` 有 2,336 行——占生产代码的 41%——装着十六个命令函数以及它们的「参数→编辑对象」映射辅助函数。它只有五个单元测试。所有天生难测的东西都堆积在同一个文件里，而下文的大部分发现就住在那里。

三个元数据引擎恰好相反：`whereexpr.rs`、`timeop.rs`、`gpx.rs`、`namedate.rs` 小而纯，测试密度 36–108%。这种「模块越大测试越少」的反相关关系，就是整个项目的形状。

## 6. 审计发现

严重级按真实用户影响判定。*已复现*表示该行为在本次审计中被实际触发过。

### F-01 `strip` 留下 XMP 与 IPTC —— 隐私承诺是假的

**位置** `src/commands.rs:2089-2109` → `src/exif.rs:82-95`

**影响** 致命。`strip` 被文档描述为「清除全部元数据（保护隐私）」。`exif::strip_all` 转交给 EXIF 引擎的 `clear_metadata`，而后者只清 EXIF 段。XMP 包与 IPTC-IIM 块从未被碰过，于是作者名、城市、位置、标题、关键词全都活了下来。命令打印 `[OK]` 并把文件计入已修改。用户在发布前清了一遍，然后照样把自己的姓名和常住城市发了出去。

**证据** 已复现。给一张 JPEG 写入 EXIF `Artist` 与 GPS、XMP `dc:title`/`dc:creator`/`photoshop:City`、IPTC `Creator`/`City`。执行 `pic-killer strip -y` 之后，`show` 仍然完整报出 XMP 与 IPTC 两段，对文件做字节级扫描仍能搜到 `Zhang San`、`Hangzhou`、`dc:creator`、`xmpmeta` 与 `8BIM`。`strip --gps` 同样只删 EXIF GPS，留下 `photoshop:City` 和自定义的 `photoshop:Location`。

端到端测试之所以通过，是因为 `tests/functest.ps1:87-94` 在清除前只写了 EXIF。

**建议** 在 `process_strip` 里于 `exif::strip_all` 之后调用 `xmp::remove_packet` 与 `iptc::remove_jpeg_iptc`——两者都已存在且有单元测试。对 `--gps`，再额外删掉 XMP 的 `exif:GPSLatitude`/`GPSLongitude` 与 `photoshop:City`/`State`/`Country`/`Location`，以及 IPTC 的 2:90/2:95/2:101。补一条端到端断言，在清除前把三套体系都写满。可以考虑加 `--keep` 白名单，让「除版权与作者外全部移除」变得可表达。

**状态** 已修复。`process_strip` 现在在一次原子写入里清除 EXIF 段、XMP 包与 IPTC 块，并报出实际清掉了哪几套；`--gps` 另外删除 XMP 的 `exif:GPS*` 属性。用当初的探针重新验证：一张写满三套元数据的照片 `strip` 之后做字节扫描，原来的姓名与地名一个都搜不到。回归断言 `F-01 …` 同时覆盖标签视图与原始字节。

### F-02 对不存在的标签名做负向 `--where` 比较会匹配每一个文件

**位置** `src/whereexpr.rs:204-220`

**影响** 高。`eval_tag` 先收集所有「名称包含查询名」的标签值，然后把 `!=` 定义为 `!eq`、`!~` 定义为 `!contains`。当这个名称压根匹配不到任何标签时，值列表为空，于是两个取反对每个文件都为真。代码无法区分「标签存在但值不同」与「根本没有这个标签」。一个笔误——比如写 `camera!=Canon`，而实际标签叫 `Make`——就会选中整个图库。

**影响被 `--where` 所把守的对象放大**：`strip`、`gps --clear`、`xmp --clear`、`iptc --clear` 全都接受它。

**证据** 已复现。四个文件（两台 Canon、一台 Nikon、一个空白）：`make!=Canon` 正确选中 2/4；`camera!=Canon` 选中 **4/4**，`nonexistenttag!=whatever` 与 `nonexistenttag!~whatever` 同样 4/4。`strip --where "camera!=Canon"` 的预览把四个文件全列为目标。

**建议** 把「不存在」与「不相等」区分开。当没有标签匹配该名称时，`!=` 与 `!~` 应当返回假而不是真——或者干脆把整条条件判为错误，因为匹配不到任何标签的名称几乎总是笔误。至少也要在某个比较的标签名在整个待处理集合上解析到零个标签时，向 stderr 发出警告。

**状态** 已修复。`apply_where` 现在会收集所有取反比较用到的标签名，在筛选之前并行地拿它们跟整个待处理集合核对一遍，哪里都匹配不到就带着可疑名称中止。`make!=Canon` 仍然照常匹配其它厂商以及根本没有 Make 的照片。

### F-03 混用 `&&` 与 `||` 会静默误解析而不是报错

**位置** `src/whereexpr.rs:105-120`

**影响** 高。`parse_expr` 先查 `||`，一旦存在就只按 `||` 切分，两半各自当作单个条件解析。像 `no-gps && make=Canon` 这一半仍含 `=`，于是被解析成对一个字面名叫 `no-gps && make` 的标签做比较，而它什么也匹配不到。表达式被接受，返回一个错误的文件集合。更糟的是，如果 `&&` 那一半用的是 `!=`，F-02 就会作用于它，使这一半对每个文件都为真。

README 把混用写作不支持，这话没错，但描述的失败模式不对：用户预期的是被拒绝，实际拿到的是静默的错误答案。

**证据** 已复现。`has-gps && make!=Canon || make=Nikon` 选中 **4/4** 个文件；同一表达式把 `!=` 换成 `=` 则选中 1/4。相比之下 `no-gps && bogusword`——不含比较运算符——会被正确地以解析错误拒绝。这正是该缺陷难以察觉的原因：会大声报错的写法和会静默出错的写法，在用户看来长得一模一样。

**建议** 切分之后，只要某个子表达式里还残留着另一个运算符就直接拒绝——两行检查，就能把静默的数据损坏变成清晰的报错。彻底的修法是换成支持括号的递归下降解析器，但这道护栏应当先行、且独立落地。

**状态** 已修复。`parse_expr` 在切分后拒绝任何仍残留另一个运算符的子表达式，并指出是哪一半。

### F-04 文档宣传的 CSV 闭环不可能跑通

**位置** `src/commands.rs:635, 654-661`（导出）对 `src/commands.rs:1610-1615`（导入）

**影响** 高。README 把「用 `show --csv` 导出、在表格里编辑、用 `apply` 写回」当作招牌流程，功能一览表也称 `apply` 是「表格里批量编辑的写回端」。但 `show --csv` 写的是五列 `file,group,name,hex,value`，而 `apply` 把前三列当作 `file,field,value` 读。于是 `field` 收到的是 IFD 分组名，`value` 收到的是标签名。表头也不会被跳过，因为跳过判断比较的是第二列是否等于字面量 `field`，而实际值是 `group`。

**证据** 已复现。把 `show --csv` 的输出直接喂给 `apply`：表头行得到 `[失败] file (不支持的文件类型：file: File does not exist!)`，数据行得到 `[失败] …（未知或暂不支持的字段 `IFD0`）`。零修改，退出码 2。

**建议** 要么给 `show` 加一个三列导出模式——比如 `--csv --for-apply`，输出 `file,field,value` 且字段名用 `apply` 认识的那套；要么让 `apply` 能识别并消化五列布局。在其中之一落地之前，README 应改口说明 `apply` 的 CSV 是手工编写的。这是设计缺口而非笔误：两种格式从来没有被对齐过。

**状态** 已修复。`show --csv --for-apply` 输出 `file,field,value`，字段名用 `apply` 认得的那套，GPS 各分量合并成一行 `gps`，写不回去的标签直接跳过。完整的「导出→编辑→写回」闭环已有端到端断言。

### F-05 RAW+JPEG 同名对的 sidecar 路径冲突，且 sidecar 写入非原子

**位置** `src/xmp.rs:676-678`、`src/commands.rs:1107-1140`

**影响** 高。`sidecar_path` 就是 `image.with_extension("xmp")`，于是 `IMG_0001.CR2` 与 `IMG_0001.JPG`——所有 RAW+JPEG 双格式相机的标准产物——都指向同一个 `IMG_0001.xmp`。`process_xmp_sidecar` 经 `run_batch` 调度，默认并行，而它用的是裸的 `std::fs::write`：没有临时文件、没有重命名，完全绕开 `commit_raw`。两个线程同时打开、截断并写入同一路径。

这同时也证伪了 `src/commands.rs:143` 那句「各写各的文件，因此并行安全」的注释。

**证据** 已复现。一个含 `IMG_0001.CR2` 与 `IMG_0001.JPG` 的目录，执行 `xmp --sidecar --title Sunrise --rating 5`，只产出了**一个** `IMG_0001.xmp`；两个文件都报 `[OK] 已写入 sidecar IMG_0001.xmp`，没有任何冲突提示。

**建议** 把 sidecar 写入接回与其它写入相同的原子替换路径。然后要么在派发前检测目标冲突并报错，要么改用 darktable 的约定——在完整文件名后追加 `.xmp`（`IMG_0001.CR2.xmp`），这样根本不会冲突。加一个 `--sidecar-style adobe|darktable` 就能同时照顾两套生态。另外，sidecar 模式目前完全忽略 `--backup`，而 `--sidecar --clear` 是硬删除，`restore` 无从恢复。

**状态** 已修复。冲突的 sidecar 目标会在动任何文件之前被检出并报错拒绝，错误里同时给出两个来源路径；sidecar 写入改走与其它写入相同的 `commit_raw` 原子路径，`--sidecar --clear` 也遵守 `--backup`。

### F-06 `verify` 检不出它自己宣称能检的元数据损坏

**位置** `src/exif.rs:52`、`src/commands.rs:2270-2281`

**影响** 高——对一个以健康检查为职责、且退出码专为 CI 门禁设计的命令而言。`verify` 里「元数据不可读」这条问题分支，只在 `load_metadata` 返回错误时触发。而 `load_metadata` 写的是 `Metadata::new_from_path(path).unwrap_or_else(|_| Metadata::new())`——任何解析失败都被吞掉并替换成空元数据，只有容器类型本身不认识才会报错。于是一张 EXIF 块被截断或损坏的 JPEG，在它眼里就是「一张没有元数据的照片」，产不出任何 issue，最终被计入「正常」。

**证据** 已复现。把一张 JPEG 的 EXIF 区域用 `0xFF` 覆写后交给 `verify`，得到 `共 1 张：正常 1，问题 0，警告 0`，退出码 0。

**建议** 增加一个会把解析错误暴露出来的加载函数，让 `verify` 用它，而写入类命令继续用宽容的那个。若不打算这么做，就从命令描述和 `cli.rs:54` 里去掉「损坏」检测的说法。

**状态** 已修复。新增的严格加载函数会把解析失败向上传递，同时把上游那个「没有 EXIF 数据」的情形——唯一消息文本稳定的那个——归一化回空元数据。三种情形均已验证：无 EXIF 算健康、有效 EXIF 算健康、块在但解析不了则报为问题并附上底层原因。

### F-07 文档里的 `gps.clear` 字段根本不存在

**位置** `src/commands.rs:1781-1784`、`:1807`

**影响** 作为文档缺陷是高——因为它让一个用户出于隐私目的执行的操作失败，而错误消息又没提示可用的写法。字段名归一化去掉 `-`、`_` 和空格，但不去点号，而匹配臂是 `"gpsclear" | "cleargps"`。文档写的 `gps.clear` 于是落到兜底分支，导致该文件整条导入中止。

**证据** 已复现。字段写 `gps.clear` 的 CSV 行得到 `[失败] …（未知或暂不支持的字段 `gps.clear`）`；同一行改成 `gpsclear` 即成功。

**建议** 把 `'.'` 加进被剥离的字符集——一个字符，文档里的写法就能用了。无论如何都要修 `README.md:371`。

**状态** 已修复。字段名归一化现在连同 `-`、`_`、空格一起把 `.` 也去掉，文档写的写法因此可用。F-14 那条误导性的未知字段消息同时改写为指向 `xmp:` / `iptc:` 前缀。

### F-08 三处用户可触发的 panic

**位置** `src/commands.rs:1580`（`parse_tz`）、`src/commands.rs:939`（`rename --pattern`）、`src/whereexpr.rs:134`

**影响** 中。三者都以 Rust panic 消息加 backtrace 提示的形式崩溃，而不是给出干净的错误。没有数据损失——三处都在任何写入之前 panic——但一个帮助文本里就明摆着推荐非 ASCII 用法（`artist~张`）的工具崩在非 ASCII 输入上，是很糟的失败方式，也削弱了「生产路径零 `unwrap`」所给人的无 panic 印象。这些 panic 来自库调用与按字节偏移切片，而不是 `unwrap`，所以数 `unwrap` 的数量根本量不到它们。

**证据** 三处均已复现。

| 输入 | 结果 |
|------|------|
| `geotag --tz 😀` | 在 `commands.rs:1580` panic |
| `geotag --tz 中中` / `中文中` | 干净报错——触发 panic 需要特定字节长度 |
| `rename --pattern "%Q"` 或 `"%"` | 在 chrono 的格式化代码里 panic |
| `--where "😀=x"`、`"no:😀"`、`"😀"` | 在 `whereexpr.rs:134` panic |
| `--where "artist~😀"`、`"has:😀"` | 不 panic |

**建议** 把 `parse_tz` 与 `whereexpr.rs` 里的固定字节偏移切片换成按字符访问或 `get(..)`。用 `StrftimeItems` 先校验 `--pattern`，遇到未知说明符时报错并指出是哪个 token。

**状态** 已修复。两处按字节偏移的切片都加了保护（改用 `get`，以及一个 ASCII 数字检查），`--pattern` 在批处理开跑前用 `StrftimeItems` 校验，同时拒绝路径分隔符。上表四种输入现在都是干净的错误。

上述清单中，以下几条现已修复，可观测的都配了回归断言：提示改到 stderr，非 TTY 且缺 `-y` 时直接报错而不是空转；`-v` 会输出真正的设置摘要；临时文件名带上进程号与递增序号，并用 `create_new` 创建，因而无法顺着预置的符号链接写出去，写入失败时也会清理；文件不存在时报「文件不存在」而不是「不支持的文件类型」；`report` 按显示宽度对齐；`show --csv` 中和公式前缀而 `--for-apply` 保持逐字；`rotate --reset` 能修复越界方向值；`restore` 两种模式都是原子的；Unix 上 rename 之后会 fsync 目录。退出码已写进用户手册（§12）。仍然开着、且属于「写进文档」而非「改掉代码」的：`show` 每个文件读三遍、整文件读入没有大小上限、XMP 与 IPTC 的单段天花板，以及 PNG EXIF 用 zTXt。

有三条候选发现在对抗性审阅中**被反驳**，未列入上表：声称 `load_metadata` 会在任何写入时抹掉元数据、声称 `apply` 缺少目录约束、以及声称只读命令的串行执行属于缺陷而非性能优化空间。

## 7. 安全性评审

安全面比正确性面好。对全部攻击面的对抗性审查没有发现内存安全暴露。

- **手写解析器是稳的。** `iptc.rs` 与 `xmp.rs` 里的 8BIM、APP13、IIM 与 PNG chunk 解析器全程边界检查完备。取自文件的长度字段在使用前都做了校验，没有未检查的切片，也没有整数溢出。恶意图片无法造成越界读。发现了两处静默截断，但它们是安全的。
- **没有 XML 实体暴露面。** `quick-xml` 默认不展开实体，所以 GPX 与 XMP 解析不存在十亿笑或外部实体风险，嵌套深度也是有界的。一点提醒：源 XMP 包里的 `DOCTYPE` 会被原样透传到写出的包里，值得剥掉。
- **实际不存在路径穿越。** `apply` 从 CSV 读目标路径且不做目录约束，对抗性审阅者检查后将其反驳：CSV 是用户自己编写的输入文件，信任级别等同于命令行本身。

真正与安全相关的问题是隐私那几条，而它们属于正确性缺陷而非漏洞：F-01（`strip` 把个人数据留在文件里）与 F-02/F-03（本用于保护文件的筛选条件可能静默失效）。对一个把「发布前清除元数据」写进用途的工具而言，F-01 是本报告中最严重的一条。

另有两条较低严重级：临时文件名完全可预测且 `File::create` 跟随符号链接，因此对目标目录有写权限的恶意本地用户可以预埋符号链接——考虑到这样的用户本就能改照片，影响有限。以及 `show --csv` 不会中和以 `=`、`+`、`-`、`@` 开头的单元格，于是当用户按 README 的建议用 Excel 打开时，图片元数据里的公式就变成了活公式。

## 8. 测试覆盖评估

这套测试在它覆盖的地方是真的好，但有一种结构性的盲区。

优点：51 个单元测试集中在 bug 真正藏身的纯逻辑上——方向复合矩阵被穷举验证为一个封闭群，时间偏移的日历运算在月末边界上被测到，GPX 插值在边界处被测到，IPTC 与 XMP 做了字节级往返并验证了无关块的保留。端到端测试用唯一能真正证明无损的方式验证无损：每次写入前后对解码像素取 SHA-256。

盲区是结构性的，而 F-01 到 F-07 每一条都落在其中：

- **端到端测试没进 CI。** 它依赖 PowerShell 与 `System.Drawing`，只能在 Windows 上手动跑。CI 在三个平台上跑 `cargo test`、`fmt` 和 `clippy`——而这些压根不会执行 `commands.rs` 的编排逻辑。
- **测试夹具太简单。** 测试造一个只有一套元数据的照片，然后就那一套做断言。`strip` 测的是只有 EXIF 的文件，这正是 F-01 能在全绿套件下存活的原因。
- **命令之间的闭环没被测过。** 每个命令都是单独测的，没有任何测试把 `show --csv` 喂给 `apply`，这正是 F-04 能存活的原因。
- **`--where` 只测了解析，没测选择语义。** `whereexpr.rs` 的六个测试全都针对 `parse`，没有任何测试检查 `matches` 对一个不存在的标签名返回什么，这正是 F-02 能存活的原因。
- **有一条断言是恒真的**（F-19），而性能套件的加速比数字受到了污染：顺序那次最先跑、`-j 4` 那次最后跑，文件缓存预热抬高了后面的成绩。`-j 4` 快过 24 线程默认值这一现象，目前无法解读。

各模块的覆盖度与模块体量成反比：`namedate.rs` 的测试代码比生产代码还多；占代码库 41% 的 `commands.rs` 只有 1.8%。

**修复之后。** 端到端断言已达 103 条，并接入 CI 的 `windows-latest` job，`commands.rs` 第一次有了自动化回归保护。每条已修复的发现都有一条以其编号命名的断言；让 F-01 得以存活的夹具弱点被直接针对：新的 `strip` 测试会把 EXIF、XMP、IPTC 都写满，然后检查**原始字节**而不只是标签视图。命令之间的闭环现在有测试了（F-04），`--where` 也从「只测解析器」变成了「测选择语义」（F-02、F-03）。

单元测试从 51 增至 73。`commands.rs` 从 5 个增至 22 个，覆盖的正是审计点名的那些纯函数：字段名归一化、`apply` 的字段词表、XMP 简称解析、时区解析、重命名模板校验与目标命名、sidecar 冲突检测，以及 CSV/JSON 转义。其中两个测试首次运行就失败，且两个都是真问题：`parse_tz` 接受了 `++08`（因为 Rust 的整数解析容忍前导正号），`filter_props` 则依赖每个调用方先把关键字转成小写 —— 这是个隐式约定，失效方式是静默地少显示几行。两者均已修复。
