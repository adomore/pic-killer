# PIC-Killer · 功能预研

> PIC-Killer 相对竞品的真实位置、用户会撞到的能力差距，以及接下来值得做什么。写给路线图看，不是写给项目脸上贴金。

[English](FEATURE-RESEARCH.md) | **中文**

## 1. 本文目的

本文回答三个问题：PIC-Killer 到底在哪些方面确实强过替代品、有哪些用户会需要而它做不到、以及在它现有的架构下哪些差距值得去补。

这里的可行性判断被一个几乎决定一切的事实约束着：PIC-Killer 的 EXIF 部分并不自己解析图像容器，而是委托给 `little_exif`，这个依赖给若干看似理所当然的功能设了硬天花板。凡是能突破这层天花板的方案，靠的都是彻底绕开这个依赖——这也是为什么 sidecar 文件会在下文反复作为 RAW 问题的答案出现。

文中引用的 F-nn 编号来自[审计报告](AUDIT.zh.md)。

## 2. 当前能力边界

PIC-Killer 今天能做什么，说得足够精确以便推理：

| 维度 | 边界 |
|------|------|
| 元数据体系 | EXIF、XMP、IPTC-IIM 三套齐全，且共用一套统一的命令面 |
| 容器，EXIF | JPEG、PNG、TIFF、WebP、HEIC、AVIF、JXL |
| 容器，XMP | 仅 JPEG 与 PNG，外加独立的 sidecar 文件 |
| 容器，IPTC | 仅 JPEG |
| RAW | 无原生读写，只有 sidecar `.xmp` |
| 视频 | 完全没有 |
| 可写 EXIF 标签 | 一份手工维护的白名单：11 个字符串标签、14 个数值与有理数标签，外加时间、GPS、方向、用户注释 |
| 批量选择 | 路径、目录、递归、扩展名过滤、内置通配符展开、元数据筛选 |
| 并行 | 只有写入类命令；只读命令是顺序的 |
| 安全 | 预览、备份、确认提示、原子替换、时间戳保留 |
| 自动化 | 退出码、JSON 与 CSV 导出、shell 补全、man 手册页 |
| 语言 | 界面与文档均为中文 |

其中三行在战略上最要紧：约 25 个可写标签的白名单、RAW 与视频的缺席、以及只有中文输出。

## 3. 竞品格局

| 工具 | 优势 | 劣势 | PIC-Killer 赢在哪 |
|------|------|------|------------------|
| ExifTool | 事实标准。数千个可写标签、数百种格式，含 RAW、视频、PDF、音频。覆盖面上无人接近 | 需要 Perl 运行时或一个几兆的打包可执行文件；逐文件进程启动让大批量很慢；单线程；选项体系出了名地难学 | 单个静态二进制、零运行时，并行写入，每个写命令都有预览与确认，且命令面是按任务而非按标签组织的 |
| exiv2 | 原生 C++、快、无运行时依赖，而且同样覆盖三套体系——最接近的真正竞品 | CLI 只是库的薄封装：`-M"set Exif.Image.Artist Ascii 张三"` 这种写法不友好；没有地理标记、没有重命名、没有 CSV 导入、没有元数据筛选 | 按任务组织的命令（`time`、`geotag`、`rename`、`apply`、`report`、`verify`）、`--where` 筛选，以及默认开启的安全模型 |
| jhead | 极小、极快、单文件，在日期偏移与按日期重命名上打磨得很好 | 仅 JPEG、仅 EXIF，可写标签极少，基本已停止维护，只有英文 | 覆盖面是严格超集，同时保持了单二进制的手感——唯一例外是 jhead 能重生成缩略图而 PIC-Killer 不能 |
| ExifCleaner | 隐私场景零学习成本：拖进去，元数据就没了。跨平台 GUI | 只能清除，不能设置、复制、地理标记或重命名；Electron 包体庞大；不可脚本化 | 可脚本化、可接入 CI、可预览——**但见 F-01：在这个竞品唯一的核心用例上，PIC-Killer 目前是错的**，因为 `strip` 会留下 XMP 与 IPTC |
| GUI 管理器（Lightroom、digiKam、XnView MP、Photo Mechanic） | 元数据编辑就在看片挑片的工作流里，有视觉反馈，单张精修体验极佳 | 安装笨重、多为商业软件；批量操作靠点击，难复现、无法审计；不可脚本化 | 那些恰恰因为机械且量大而在 GUI 里很痛苦的操作：给 4,000 张照片统一偏移 +2h、用轨迹给整趟旅行地理标记、给一张卡的导出批量改名 |

**诚实的定位。** PIC-Killer 不是在覆盖面上和 ExifTool 竞争，也不该假装如此。它站得住的位置是：一个零运行时的单文件二进制，做好摄影师真正需要的那二十来个批量操作，并且同时具备三个别家都没凑齐的属性——安全是默认而非开关、三套元数据共用同一套选择模型、以及中文优先的使用手感。

这三条主张里有两条目前是有窟窿的。安全被 F-01 与 F-05 拆台，统一选择模型被 F-02 与 F-03 拆台。补上它们比这份清单上的任何新功能都值钱。

## 4. 能力差距

按真实用户撞上的概率排序。

| 差距 | 影响 | 说明 |
|------|------|------|
| `strip` 不删 XMP 与 IPTC | 高 | 这不是差距而是缺陷——见 F-01。列在这里是因为它同时也是 ExifCleaner 存在的理由 |
| 无原生 RAW 读写，且 sidecar 这条绕行路线会冲突 | 高 | RAW 是产品上最大的窟窿，而绕行方案本身带着数据丢失缺陷（F-05） |
| 可写标签是约 25 个名字的白名单 | 高 | 用户想要的每一个新标签都得改代码。这是与 ExifTool 之间最大的功能距离 |
| XMP 仅支持 JPEG 与 PNG，而 `--ext` 默认却含 TIFF 与 WebP | 高 | 自找的：对着 TIFF 目录第一次跑 `xmp` 只会得到一片跳过，看起来像工具坏了 |
| 完全没有视频元数据 | 高 | 现代手机图库大约一半是视频，而按时间重命名与地理标记对视频同样适用 |
| 界面与文档只有中文 | 高 | 面向中文世界之外，这是最大的采用障碍 |
| 只读命令单线程，且 `--where` 逐条件重复读盘 | 中 | 「快」是明确的定位主张，但目前只对写入成立（F-17） |
| MakerNote 字节保住了，但内部偏移没被修正 | 中 | 损坏的 MakerNote 比丢失的更糟：下游工具会去解析垃圾，而不是报告缺失 |
| `rename` 只支持基于拍摄时间的 strftime 模板 | 中 | 没有文件名占位符、没有序号、不能建日期子目录、没有 mtime 兜底 |
| 没有选择性清除 | 中 | 「除版权与作者外全部移除」这个最常见的专业需求无法表达 |
| 撤销只有逐文件 `.bak`，没有操作日志 | 中 | 需要事先有预见，且反复修改会全部塌缩到第一次的备份上 |
| 无配置文件、无预设 | 中 | 每次调用都要重敲整套选项，把用户推向自己写包装脚本 |
| XMP 与 IPTC 写入被限制在单个 64 KB 的 JPEG 段内 | 中 | 带显影参数或深层关键词树的 Lightroom 包体经常超过这个上限 |
| PNG 的 EXIF 写成传统 zTXt，从不用标准 `eXIf` chunk | 中 | 与现代读取方之间的互操作陷阱 |
| 内嵌缩略图既不更新也无法替换 | 中 | 旋转之后缩略图仍显示旧方向 |
| `verify` 没有结构化输出 | 中 | 主打 CI 门禁，却只暴露一个退出码和中文文本 |

## 6. 可行性详析

### 6.1 让 `strip` 名副其实

全表性价比最高的一项，而且它补的是正确性缺口而非功能缺口。两块积木都已在仓库内且有单元测试：`xmp::remove_packet` 与 `iptc::remove_jpeg_iptc`。`process_strip` 只需在 `exif::strip_all` 之后把两者都调一遍。对 `--gps`，再额外删掉 XMP 的位置类属性与 IPTC 的 2:90/2:95/2:101。`--keep` 白名单是同一趟处理的自然延伸，能让那个常见的专业需求变得可表达。

不牵涉任何上游依赖——依赖里的 `clear_metadata` 本来就只管 EXIF 段，另外两段早已由本仓库自己的段手术代码在处理。

### 6.2 重写 `--where` 解析器

这是一个披着功能外衣的正确性修复。两个互相独立的问题：切分器无法表达混用运算符且会静默误解析（F-03），以及负向比较无法区分「标签名不存在」与「值不相等」（F-02）。

值得分阶段做。先加一道护栏：切分之后只要子表达式里还残留另一个运算符就拒绝——两行代码，立刻把静默的数据损坏变成报错。然后再上带括号与优先级的递归下降解析器，这是有成熟套路的工作，且已有测试模块托底。「不存在 vs 不相等」的修复独立于前两者，且应当最先落地，因为只有它带着数据丢失后果。

### 6.3 写前护栏

单位代码价值最高的一项，同时也是候选 7、11、14、19 的前置条件。今天没有任何东西验证一次写入是否产出了可读的文件。护栏应当在写前检查容器类型是否与扩展名声称的一致，写后重新读回文件、确认目标标签存在且像素数据未变。

这件事之所以要紧，是因为 EXIF 依赖有三个已知的危险行为：它按扩展名而非内容判断文件类型；它的 TIFF 写入是整文件重建——对伪装成 TIFF 的 CR2 与 NEF 是毁灭性的；以及 MakerNote 会被搬动而不修正偏移。要碰上述任何一种格式又不想赌运气，护栏层就是唯一的办法。

### 6.4 通往 RAW 的 sidecar 路线

原生 RAW 解析在可接受的成本内够不着，而通过现有依赖去尝试更是主动犯险——它的 TIFF 整文件重建就摆在那里。sidecar 恰恰是 Lightroom 与 darktable 用户本来就生活其中的工作流，所以这条路能用零头的工作量交付 RAW 的绝大部分实用价值，而它之所以可行，正是因为完全绕开了那个依赖。

三块工作，全部限制在本仓库内。先修冲突——不管路线图怎么排，它都是一个数据丢失缺陷（F-05）——改用不可能冲突的命名方案，最好把 Adobe 与 darktable 两套约定都提供。然后加 sidecar 读回，让 `show` 与 `--where` 能看见那些容器解析不了的文件的 sidecar 内容。最后扩展 sidecar 去承载 EXIF 等价与 IPTC 等价的属性——XMP 本来就有对应词汇表——从而让 RAW 用户在完全不打开 RAW 文件的前提下用上 `time`、`gps` 和 `geotag`。

### 6.5 通用标签写入

单独一项就最能拉近与 ExifTool 功能距离的改动，因为它把一份约 25 个名字的封闭白名单变成了开放接口。上游能力其实早就存在且闲置：依赖暴露了携带值、十六进制码与分组的 `Unknown*` 标签变体。

工作量在于一套新的 CLI 表面——形如 `--set-tag "EXIF:0x9291:STRING=00"`——外加一个把分组、hex、格式映射到正确变体的解析器。风险在于这等于递给用户一把上了膛的枪：往任意标签写入畸形值，正是候选 3 的写后自校验存在的意义，所以那一项应当先落地。友好的具名选项要保留作为顺手的正门；通用形式是逃生舱，不是替代品。

## 7. 建议路线图

**现在——正确性优先于任何新能力。** 候选 1、2，以及候选 4 里修冲突的那一半，加上审计里那些小修补。这里每一条关闭的都是「工具做的事和它说的事不一致」的情形。在一个不会清除的 `strip` 之上继续叠功能，只会让问题复利。

**接着——让现有的主张成真。** 候选 3、5、6。护栏、并行读、端到端测试进 CI。这一版之后，「快」对读取也成立了，最大的模块也不再裸奔。这些全都用户不可见，但正是它们让下一版敢动手。

**然后——扩大受众。** 候选 8、9、12。英文输出是采用率上最大的单一杠杆，且架构成本为零。更强的 `rename` 模板与预设，是最常把批量用户逼去自己写包装脚本的两件事。

**再然后——扩大能力面。** 候选 7、10、11。通用标签写入、全命令结构化输出、完整的 sidecar RAW 流程。这些功能会改变工具的用途定位，而每一项都依赖第二阶段的护栏。

**以后，如果出现需求。** 候选 13 到 17。都站得住，但都不紧急。

**除非有真实理由，否则不做。** 候选 18 与 19。MakerNote 保全价值很高但根因在上游；视频则是一个戴着相似帽子的另一个问题域。

## 8. 明确不建议做的

**用感知哈希做近似重复检测。** 这个项目从来没有解码过一个像素——整棵依赖树里没有任何图像编解码器，这正是发布二进制那么小、无损保证那么容易推理的原因。为了找视觉相似的照片而引入解码器，会同时破坏这两个属性，换来的还是一个不在工具用途之内的功能。按内容哈希做精确去重不需要解码器，那才是值得有的版本。

**去追 ExifTool 的标签覆盖面。** 手工维护的表永远追不上，硬追只会让每次发版都变成抄写工作。候选 7 的通用标签写入才是正解：把接口打开，而不是把它枚举完。

**原生 RAW 容器解析。** 代价高、格式又多又私有，而现有依赖的 TIFF 写入会毁掉这些文件。sidecar 能在没有这些风险的前提下交付工作流价值。

**交互式 TUI。** CLI 已经提供了 TUI 主要会提供的东西：预览、确认提示、以及画在 stderr 上的进度条。做它等于用一整套新依赖换一个现有界面已经满足的需求。

**为候选 8 的英文输出引入 i18n 框架。** 两种语言撑不起那套机械。编译期字符串表就够了，甚至干脆把界面语言定为英文、文档保留中文也是相称的做法。真正需要慎重决定的是**输出**说哪种语言，因为脚本和测试要解析它。
